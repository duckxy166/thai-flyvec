# การตัดสินใจเชิงออกแบบ

บันทึกการตัดสินใจที่กระทบผลการทดลอง ข้อที่มาจาก Project Proposal (CS374) ระบุไว้ว่า "ตาม proposal" ถ้าจะเปลี่ยนข้อใด ให้แก้ไฟล์นี้ผ่าน PR พร้อมเหตุผล

## D1 คลังข้อความ

- ใช้ Thai Wikipedia บางส่วน ราว 10 ล้านโทเคนหลังตัดคำ เพื่อให้เทรนบน CPU หรือ Google Colab ได้ (ตาม proposal)
- เลือกบทความด้วย seed คงที่ และบันทึกรายชื่อบทความที่ใช้ เพื่อให้รันซ้ำได้
- ทุกโมเดลใช้คลังข้อความ ผลการตัดคำ (newmm) และคลังศัพท์ 20,000 คำชุดเดียวกัน

## D2 รูปแบบ input ของ FlyVec

input ตามนิยามในงานต้นแบบคือเวกเตอร์ 0/1 ยาว 2 × 20,000 = 40,000 มิติ (ครึ่งแรกคือบริบท ครึ่งหลังคือคำเป้าหมาย) แต่มีค่า 1 ไม่เกิน w ตำแหน่ง จึง**ไม่สร้างเวกเตอร์ dense**

- เก็บแต่ละหน้าต่างเป็นดัชนีคำ: array `int32` ขนาด `(n_windows, w)` ตำแหน่งกลางคือคำเป้าหมาย คำนอกคลังศัพท์แทนด้วย `-1`
- คำนวณ activation จากผลรวมของคอลัมน์ `W` ที่ตำแหน่งที่ active หารด้วยความถี่คำ (บริบทใช้คอลัมน์ `id`, เป้าหมายใช้คอลัมน์ `20,000 + id`)
- ข้ามหน้าต่างที่คำเป้าหมายอยู่นอกคลังศัพท์
- หน้าต่างไม่ข้ามขอบประโยค

ผลเท่ากับนิยามเดิมทุกประการ แต่ใช้หน่วยความจำน้อยลงราว 40,000 / w เท่า

## D3 hash แบบ static ของคำ

`hash(word, k)` ป้อนเฉพาะคำเป้าหมาย (ครึ่งบริบทเป็น 0) แล้วเลือก k Kenyon cells ที่ activation สูงสุดเป็น 1 ตามงานต้นแบบ ค่า k ใช้ตอนสร้าง hash เท่านั้น **ไม่ต้องเทรนใหม่เมื่อเปลี่ยน k**

## D4 ตัววัดความคล้าย

ใช้ **cosine similarity กับทุกโมเดล**

สำหรับ hash ที่มี 1 ครบ k ตัวพอดี cosine = overlap / k, Jaccard = overlap / (2k − overlap) และ Hamming = 2k − 2 · overlap ทั้งสามเป็นฟังก์ชันทางเดียวของ overlap จึงให้ลำดับเดียวกัน และ Spearman ρ เท่ากันทุกตัว การเลือก cosine จึงไม่กระทบผล และใช้โค้ดเดียวกับเวกเตอร์ทศนิยมได้

## D5 word2vec แบบไบนารี

- เทรน word2vec 300 มิติ (ตาม proposal) แล้วตั้ง k ค่าสูงสุดของแต่ละเวกเตอร์เป็น 1 ที่เหลือเป็น 0 (ตาม proposal)
- ใช้ k ชุดเดียวกับ FlyVec: 4, 8, 16, 32, 64
- ข้อจำกัดที่ต้องรายงาน: FlyVec มี 400 บิต ส่วน word2vec ไบนารีมี 300 บิต ความหนาแน่นที่ k เดียวกันจึงต่างกัน (เช่น k = 64 คือ 16% กับ 21%)

## D6 baseline

- word2vec และ fastText (gensim) 300 มิติ, window เท่ากับ FlyVec, จำนวน epoch เท่ากัน
- ผลหลักจำกัดทุกโมเดลไว้ที่คลังศัพท์ 20,000 คำชุดเดียวกัน fastText จึงไม่ได้สร้างเวกเตอร์ให้คำ OOV จาก subword
- รายงาน fastText ที่ใช้ subword กับคำ OOV เป็นแถวเพิ่มเติม เพื่อแสดงว่า subword ช่วยเรื่อง OOV ในภาษาไทยได้แค่ไหน

## D7 การประเมินความคล้ายคลึงของคำ

- คู่คำใน TH-WordSim-353 / TH-SimLex-999 ที่คำใดคำหนึ่งไม่อยู่ในคลังศัพท์ในรูปคำเดียว นับเป็น OOV และไม่นำมาคิด ρ
- รายงานสัดส่วนคู่คำ OOV คู่กับ ρ ทุกครั้ง และคำนวณ ρ ของทุกโมเดลบนชุดคู่คำเดียวกัน (คู่ที่ทุกโมเดลรู้จัก)

## D8 เวกเตอร์ประโยคสำหรับ sentiment

- ตัดคำด้วย newmm เช่นเดียวกับคลังข้อความ
- เวกเตอร์ประโยค = ค่าเฉลี่ยของเวกเตอร์คำที่อยู่ในคลังศัพท์ สำหรับ hash ไบนารี ค่าเฉลี่ยคือสัดส่วนคำที่กระตุ้นแต่ละ Kenyon cell
- ประโยคที่ไม่มีคำในคลังศัพท์เลย ใช้เวกเตอร์ศูนย์ และรายงานจำนวนประโยคเหล่านี้
- logistic regression เลือกค่า C จากชุด validation แล้วรายงาน accuracy และ macro-F1 บนชุด test ของ wisesight_sentiment

## D9 การทดลองและ seed

- w ∈ {5, 11, 15} โดย 11 เป็นค่าเริ่มต้นตามงานต้นแบบ
- k ∈ {4, 8, 16, 32, 64} ไม่ต้องเทรนใหม่ (D3)
- 3 seed (0, 1, 2) ต่อการตั้งค่า รายงานค่าเฉลี่ย ± ส่วนเบี่ยงเบนมาตรฐาน
- จำนวนรอบเทรน FlyVec: 3 ค่า w × 3 seed = 9 รอบ ส่วน baseline ใช้ 3 ค่า w × 3 seed เช่นกัน

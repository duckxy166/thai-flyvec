# การตัดสินใจเชิงออกแบบ

บันทึกการตัดสินใจที่กระทบผลการทดลอง ข้อที่มาจาก Project Proposal (CS374) ระบุไว้ว่า "ตาม proposal" ถ้าจะเปลี่ยนข้อใด ให้แก้ไฟล์นี้ผ่าน PR พร้อมเหตุผล

## D1 คลังข้อความ

- ใช้ Thai Wikipedia บางส่วน ราว 10 ล้านโทเคนหลังตัดคำ เพื่อให้เทรนบน CPU หรือ Google Colab ได้ (ตาม proposal)
- เลือกบทความด้วย seed คงที่ และบันทึกรายชื่อบทความที่ใช้ เพื่อให้รันซ้ำได้
- ทุกโมเดลใช้คลังข้อความ ผลการตัดคำ (newmm) และคลังศัพท์ 20,000 คำชุดเดียวกัน
- แหล่งข้อมูล: `wikimedia/wikipedia` config `20231101.th` ผ่าน `datasets` (เป็นข้อความล้วนแล้ว ไม่ต้อง parse dump `.xml.bz2`) สลับลำดับบทความด้วย seed 0 เก็บไว้ 80 ล้านอักขระ (`scripts/download_data.py`) แล้วตัดที่บทความแรกที่ทำให้ครบ 10 ล้านโทเคน (`scripts/preprocess_corpus.py`) รายชื่อบทความที่ใช้จริงอยู่ใน `data/processed/articles_used.txt`
- ตัดประโยคที่ขึ้นบรรทัดใหม่ และที่ช่องว่างซึ่งมีอักษรไทยทั้งสองข้าง (ภาษาไทยไม่มีเครื่องหมายจบประโยค และวิธีนี้ไม่ตัด "พ.ศ. 2563" หรือวลีภาษาอังกฤษ) ทิ้งโทเคนที่ไม่มีตัวอักษรหรือตัวเลข (เครื่องหมายวรรคตอน) และแปลงอักษรละตินเป็นตัวเล็ก

## D2 รูปแบบ input ของ FlyVec

input ตามนิยามในงานต้นแบบคือเวกเตอร์ 0/1 ยาว 2 × 20,000 = 40,000 มิติ (ครึ่งแรกคือบริบท ครึ่งหลังคือคำเป้าหมาย) แต่มีค่า 1 ไม่เกิน w ตำแหน่ง จึง**ไม่สร้างเวกเตอร์ dense**

- เก็บแต่ละหน้าต่างเป็นดัชนีคำ: array `int32` ขนาด `(n_windows, w)` ตำแหน่งกลางคือคำเป้าหมาย คำนอกคลังศัพท์แทนด้วย `-1`
- คำนวณ activation จากผลรวมของคอลัมน์ `W` ที่ตำแหน่งที่ active (บริบทใช้คอลัมน์ `id`, เป้าหมายใช้คอลัมน์ `20,000 + id`) คำบริบทที่ซ้ำในหน้าต่างเดียวกันนับครั้งเดียว เพราะ input เป็น 0/1
- เลือก Kenyon cell ที่ชนะจาก activation ปกติ `<W_μ, v>` ตามสมการ (1) ของงานต้นแบบ ส่วนการถ่วงด้วย 1/ความถี่คำ (`v/p`) ใช้ในค่า energy และการ update เท่านั้น ในการทดลองเบื้องต้นบนข้อความ ~0.5 ล้านโทเคน การเลือกผู้ชนะจาก `<W_μ, v/p>` ให้ ρ ต่ำกว่าทุกครั้ง เพราะคำเป้าหมายที่พบน้อยมีน้ำหนักมากจนตัดสินผู้ชนะแทนบริบท
- ข้ามหน้าต่างที่คำเป้าหมายอยู่นอกคลังศัพท์
- หน้าต่างไม่ข้ามขอบประโยค: ตำแหน่งที่เลยต้นหรือท้ายประโยคเป็น `-1` (ไม่ทิ้งหน้าต่างนั้น เพราะประโยคไทยที่ตัดตามช่องว่างมักสั้นกว่า w)

ผลเท่ากับนิยามเดิมทุกประการ แต่ใช้หน่วยความจำน้อยลงราว 40,000 / w เท่า

## D3 hash แบบ static ของคำ

`hash(word, k)` ป้อนเฉพาะคำเป้าหมาย (ครึ่งบริบทเป็น 0) แล้วเลือก k Kenyon cells ที่ activation สูงสุดเป็น 1 ตามงานต้นแบบ ค่า k ใช้ตอนสร้าง hash เท่านั้น **ไม่ต้องเทรนใหม่เมื่อเปลี่ยน k**

## D4 ตัววัดความคล้าย

ใช้ **cosine similarity กับทุกโมเดล**

สำหรับ hash ที่มี 1 ครบ k ตัวพอดี cosine = overlap / k, Jaccard = overlap / (2k − overlap) และ Hamming = 2k − 2 · overlap ทั้งสามเป็นฟังก์ชันทางเดียวของ overlap จึงให้ลำดับเดียวกัน และ Spearman ρ เท่ากันทุกตัว การเลือก cosine จึงไม่กระทบผล และใช้โค้ดเดียวกับเวกเตอร์ทศนิยมได้

## D5 word2vec แบบไบนารี

- เทรน word2vec 300 มิติ (ตาม proposal) แล้วตั้ง k ค่าสูงสุดของแต่ละเวกเตอร์เป็น 1 ที่เหลือเป็น 0 (ตาม proposal)
- ใช้ k ชุดเดียวกับ FlyVec: 4, 8, 16, 32, 64
- ข้อจำกัดที่ต้องรายงาน: FlyVec มี 400 บิต ส่วน word2vec ไบนารีมี 300 บิต ความหนาแน่นที่ k เดียวกันจึงต่างกัน (เช่น k = 64 คือ 16% กับ 21%)

## D6 baseline

- word2vec และ fastText (gensim) 300 มิติ, window เท่ากับ FlyVec, จำนวน epoch เท่ากัน (ค่าที่ตั้งทั้งหมดอยู่ใน D10)
- ผลหลักจำกัดทุกโมเดลไว้ที่คลังศัพท์ 20,000 คำชุดเดียวกัน fastText จึงไม่ได้สร้างเวกเตอร์ให้คำ OOV จาก subword
- รายงาน fastText ที่ใช้ subword กับคำ OOV เป็นแถวเพิ่มเติม เพื่อแสดงว่า subword ช่วยเรื่อง OOV ในภาษาไทยได้แค่ไหน

## D7 การประเมินความคล้ายคลึงของคำ

- คู่คำใน TH-WordSim-353 / TH-SimLex-999 ที่คำใดคำหนึ่งไม่อยู่ในคลังศัพท์ในรูปคำเดียว นับเป็น OOV และไม่นำมาคิด ρ
- รายงานสัดส่วนคู่คำ OOV คู่กับ ρ ทุกครั้ง และคำนวณ ρ ของทุกโมเดลบนชุดคู่คำเดียวกัน (คู่ที่ทุกโมเดลรู้จัก)

## D8 เวกเตอร์ประโยคสำหรับ sentiment

- ตัดคำด้วย newmm เช่นเดียวกับคลังข้อความ
- เวกเตอร์ประโยค = ค่าเฉลี่ยของเวกเตอร์คำที่อยู่ในคลังศัพท์ สำหรับ hash ไบนารี ค่าเฉลี่ยคือสัดส่วนคำที่กระตุ้นแต่ละ Kenyon cell
- ประโยคที่ไม่มีคำในคลังศัพท์เลย ใช้เวกเตอร์ศูนย์ และรายงานจำนวนประโยคเหล่านี้
- logistic regression (หลัง standardize ฟีเจอร์) เลือกค่า C จาก {0.01, 0.1, 1, 10, 100} ด้วย macro-F1 บนชุด validation (ชุดข้อมูลไม่สมดุล) แล้วรายงาน accuracy และ macro-F1 บนชุด test ของ wisesight_sentiment
- ข้อความ wisesight ผ่าน normalize แบบเดียวกับคลังข้อความ (`clean_wiki_text`) ก่อนตัดคำ

## D9 การทดลองและ seed

- w ∈ {5, 11, 15} โดย 11 เป็นค่าเริ่มต้นตามงานต้นแบบ
- k ∈ {4, 8, 16, 32, 64} ไม่ต้องเทรนใหม่ (D3)
- 3 seed (0, 1, 2) ต่อการตั้งค่า รายงานค่าเฉลี่ย ± ส่วนเบี่ยงเบนมาตรฐาน
- จำนวนรอบเทรน FlyVec: 3 ค่า w × 3 seed = 9 รอบ ส่วน baseline ใช้ 3 ค่า w × 3 seed เช่นกัน

## D10 ค่าที่ตั้งในการเทรน

FlyVec (`src/thai_flyvec/flyvec.py`)

- K = 400 Kenyon cells, epoch = 3, mini-batch 1,024 หน้าต่าง
- เริ่มน้ำหนักจาก N(0, 1) แล้วปรับให้แต่ละ cell มีความยาว 1
- update ของแต่ละ mini-batch หารด้วยค่าสัมบูรณ์สูงสุดของมัน แล้วคูณ learning rate ที่ลดเชิงเส้นจาก 1.0 ถึง 0 ตามโค้ดของ Krotov & Hopfield (2019) ที่ FlyVec ต่อยอด learning rate จึงเป็นขนาดการเปลี่ยนสูงสุดของน้ำหนักหนึ่งตัวในก้าวแรก
- learning rate 1.0 เลือกจากการทดลองเบื้องต้นบนข้อความ wisesight ~0.5 ล้านโทเคน (1 seed): ที่ 0.01 คำใกล้เคียงไม่เกี่ยวข้องกันเลย ที่ 0.3 เริ่มเกี่ยวข้อง และ 1.0 ได้ ρ สูงสุดในชุด 0.3, 1, 3 แต่ผลแกว่งมากเพราะข้อมูลน้อย ผลใน `results/` ทั้งหมดใช้ค่านี้

- ตั้งแต่ #36 `fit` เก็บน้ำหนักเป็น V × s (สเกลหนึ่งค่าต่อ cell) ส่วน dense ของ update จึงเปลี่ยนแค่ s และ V เปลี่ยนเฉพาะตำแหน่งที่ active ผลเท่าเดิมยกเว้น rounding ของทศนิยม บนคลังข้อความจริง 300 mini-batch (w = 11) เร็วขึ้น 5.1 เท่า (68.5 → 13.3 ms ต่อ batch บนเครื่องเดียวกัน) น้ำหนักต่างจากเดิมไม่เกิน 3 × 10⁻⁷ และรหัส hash ที่ k = 16, 64 เหมือนเดิมทุกคำ เวลาเทรนและขนาดใน `results/` ยังเป็นของ implementation เดิม ต้องวัดใหม่ถ้าจะรายงานเวลาของ implementation นี้
- ที่ learning rate 3 การเทรนไวต่อ rounding มาก: แม้ implementation dense เดิมเอง ถ้าเปลี่ยน rounding เพียงจุดเดียว น้ำหนักก็แยกจากกันภายในราว 20 ก้าว ผลของสอง implementation ที่ lr นี้จึงต่างกันในรายละเอียดได้ แต่ควรต่างกันในระดับเดียวกับการเปลี่ยน seed

word2vec และ fastText (`src/thai_flyvec/baselines.py`)

- skip-gram (`sg=1`), negative sampling 5, subsampling ค่าเริ่มต้นของ gensim (`1e-3`)
- `window = w // 2` (gensim นับคำแต่ละข้าง FlyVec นับทั้งหน้าต่าง) และ `shrink_windows=False` ให้หน้าต่างยาวคงที่เหมือน FlyVec
- คลังศัพท์มาจาก `build_vocab_from_freq` ด้วยคำและความถี่ชุดเดียวกับ FlyVec คำนอกคลังศัพท์จึงถูกตัดออกจากประโยคก่อนเลื่อนหน้าต่าง (พฤติกรรมเดียวกับ `min_count` ของ gensim) ต่างจาก FlyVec ที่เว้นตำแหน่งไว้เป็น `-1`
- fastText ใช้ n-gram bucket 200,000 (ค่าเริ่มต้น 2,000,000 ทำให้โมเดลใหญ่ราว 2.4 GB ต่อรอบ) ขนาดโมเดล fastText ที่รายงานจึงขึ้นกับค่านี้
- `workers = 4` ทำให้ผลต่างกันเล็กน้อยแม้ใช้ seed เดิม ถ้าต้องการผลซ้ำได้ทุกบิตให้ใช้ `--workers 1` (ช้ากว่า)
